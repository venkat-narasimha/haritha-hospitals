# Leave Ledger Entry — Intake Sheet

**DocType:** `Leave Ledger Entry` (submittable, append-only)
**Module:** HR / Leave Management
**Autoname rule:** default Frappe hash (no explicit `naming_series` in stock schema)
**Stock-required fields:** 1 (`company`)
**Stock-optional fields:** 13+
**Custom fields:** 0 (per `haritha_hospital/fixtures/custom_field.json` Section 1)

> **Note:** Leave Ledger Entry is the **append-only audit trail** of all leave-balance movements. It is normally auto-generated by Leave Allocation (Allocation), Leave Application (Application), and Leave Encashment workflows. This sheet is for **manual corrections only** — backdated allocations, retroactive encashments, or balance restorations after a manual ledger fix.

## Purpose

Per-employee, per-Leave-Type row recording a single delta to the leave balance. Each row carries a `leaves` value (positive = credit / increase, negative = debit / decrease) and a `transaction_type` pointing at the source DocType (Leave Allocation, Leave Application, or Leave Encashment). The current leave balance for an (employee, leave_type) pair is computed as the sum of all `leaves` values across non-cancelled rows.

The `transaction_type` field is **Link→DocType** (a meta-Link pointing at the `DocType` DocType itself, NOT a Select). This is unusual — most Link fields point at a specific DocType. The actual values are DocType names like `Leave Allocation`, `Leave Application`, `Leave Encashment`, or `Leave Encashment`. The companion `transaction_name` is a Dynamic Link that resolves against whatever `transaction_type` is set to (e.g., if `transaction_type="Leave Application"`, then `transaction_name` must be a real Leave Application name).

There is **no `transaction_date` field** in the stock schema (Section 4 lists 14 fields, none called `transaction_date`). The coverage period is captured by `from_date` / `to_date`. Transaction ordering is by `creation` time (or `from_date` for ties).

## Migration notes (from research §7)

- **Gotcha #1 — `get_doc()` doctype key:** Any future custom import script must inject `{"doctype": "Leave Ledger Entry", ...}` before constructing the document.
- **Gotcha #14 — leave module unpopulated at go-live.** 0 Leave Ledger Entries at single-site deployments at go-live. The Leave Ledger is created automatically as the client starts submitting Leave Allocations and Leave Applications. This template exists for forward-compatibility and for any backfill from a legacy HRIS.
- **Gotcha #7 — Employee ID remap by `employee_name`.** Same constraint as the other three transaction templates. The upload script remaps the `employee` field using `employee_name` as the join key. Client CSV MUST supply both `employee` (original) and `employee_name` (the join key), even though both are stock-optional.
- **Ledger is append-only.** Frappe enforces this via the `LeaveLedgerEntry.on_cancel()` hook — cancelling a Submitted entry does NOT delete it; it inserts a compensating row with the inverse `leaves` delta. Never re-import a Cancelled entry with the same `name` — use a new entry instead.
- **`transaction_type` is a `Link→DocType`** (per Section 4 — NOT a Select with Allocation/Application/Encashment as some older templates show). Values are literal DocType names: `Leave Allocation`, `Leave Application`, `Leave Encashment`, `Leave Policy Assignment`, etc. Setting an invalid DocType name will fail `LinkValidationError`.
- **`transaction_name` is a Dynamic Link** — it resolves against whatever `transaction_type` is set to. If `transaction_type="Leave Application"`, then `transaction_name` must be a valid Leave Application name on the target site. Optional Links are not strictly validated at insert time (link drops silently if the target row does not exist).
- **No `transaction_date` in stock schema.** The coverage period is captured by `from_date` / `to_date`. Older intake sheets that include a `transaction_date` column will be silently dropped by Data Import (the stock fieldname does not exist).
- **`leaves` balance validation.** The Frappe controller checks that the post-transaction balance equals the previous balance + `leaves`. The upload script pre-computes the expected running balance per (employee, leave_type) before insert; rows that would invalidate the sequence are skipped with a warning.
- **Transaction ordering matters.** Ledger entries are processed in `creation` order (then `from_date` order for ties). Out-of-order imports are allowed but recompute balances per-entry, so the FINAL balance reflects the last-inserted row per (employee, leave_type). Upload in chronological order to avoid confusion in audit reports.
- **`docstatus=1` (Submitted) is required.** Draft ledger entries do NOT contribute to the Leave Balance calculation shown on Employee dashboards. Submit all imported rows to make the balance visible. (Note: `docstatus` is intentionally OMITTED from this template — Data Import handles it via the standard Import File contract.)
- **`transaction_type` and `transaction_name` should match.** When manually injecting ledger rows, set `transaction_name` to the actual name of the source Allocation/Application record. A mismatch leaves an orphan ledger row that cannot be traced back to its origin.

## Healthcare-specific extensions

None required as standard. Leave Ledger Entry has no custom fields in this project (`haritha_hospital` per Section 1). Hospital context flows from the Employee's `department` and the Leave Type's properties (`is_lwp`, `is_carry_forward`, `allow_encashment`).

If a client requires tracking clinical-staff leave accrual rules separately (e.g., distinct carry-forward windows for nurses vs doctors), that logic should be encoded on the **Leave Type** (template `11_leave_type.csv`), not on the ledger.

## When to use this sheet

| Scenario | Use this sheet? |
|---|---|
| Standard leave application approval | **No** — Leave Application auto-creates Application row on submit |
| Standard leave allocation | **No** — Leave Allocation auto-creates Allocation row on submit |
| Retroactive encashment correction | **Yes** — manual Encashment row |
| Balance restoration after data fix | **Yes** — manual Allocation row with note |
| Carry-forward from previous period | **No** — Leave Allocation handles via `carry_forward=1` and `carry_forwarded_leaves_count` |
| Backdated leave application (legacy system) | **Yes** — manual Application row |
| Compensatory leave grants | **No** — Compensatory Leave Request handles |
| LWP posting | **Yes** — manual Application row with `is_lwp=1` and matching Leave Type `is_lwp=1` |

## Common client mistakes

- Supplying `leaves` (post-balance) that contradicts `leaves_added` (delta) — note: there is NO `leaves_added` field in stock; only `leaves` (which IS the delta, not the balance). Setting both `leaves` and a separate `leaves_added` column will silently drop `leaves_added`.
- Using `transaction_type=Application` without `transaction_name` link — breaks traceability to the originating request.
- Using `transaction_type=Allocation` without `transaction_name` link — breaks traceability.
- Including a `transaction_date` column — silently dropped (field does not exist in stock schema).
- Cancelling (`docstatus=2`) the wrong ledger entry — affects ALL downstream balance calculations for that employee + leave type.
- Forgetting `transaction_type` — defaults to empty; the row is valid but uncategorised in audit reports.
- Using a Select value like `Allocation` instead of the DocType name `Leave Allocation` — fails `LinkValidationError` (this field is `Link→DocType`, not Select).
- Setting `is_carry_forward=1` on a non-Allocation row — silently dropped (the field is only meaningful for Allocation rows).
- Setting `is_expired=1` without a negative `leaves` value — the controller expects a debit delta on Expiration rows.
