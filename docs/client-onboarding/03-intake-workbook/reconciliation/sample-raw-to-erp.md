# Reconciliation Sample — Raw Excel to Frappe HR Records

> **Purpose:** For client assurance. Shows, side-by-side, what a raw Excel row
> looked like and what record it became in the Frappe HR instance after migration.
> Clients use this to audit the mapping between their source data and our system.

> **Source-of-truth:** `scripts/migrate_master_data.py` (the actual code that
> wrote records to the target Frappe HR instance).

> **Generic examples throughout.** All names, IDs, and values below are
> illustrative. The pattern is what matters; the exact names don't.

> **Last updated:** 2026-09-15

---

## How to read this document

Each section is one DocType. Within a section, you'll find:

- **Input (raw Excel)** — what the client's spreadsheet looked like
- **Output (Frappe HR record)** — what record the migration created, including
  the Frappe HR `name` field (e.g., `HR-EMP-00001`)
- **Transformation notes** — what changed during migration and why
  (e.g., column rename, value lookup, split, derivation)

> **Conventions used in this doc**
> - `name` = Frappe HR's primary identifier (visible in URLs, Link fields, exports).
> - `employee_name` = the display name (what HR sees in dropdowns). The
>   client supplies this in the CSV; the migration script uses it as the join key
>   to remap production IDs into the target site IDs (see Gotcha #7).
> - Placeholder dates use `2025-09-XX` purely to keep rows readable; the
>   pattern is what matters.
> - `Site A` / `Site B` are generic branch names; `Department A` / `Department B`
>   are generic department names. No real hospital identifiers appear.

## Example 1: Employee

### Input (raw Excel — `10_employee.csv`)

```csv
employee_name,employee_number,first_name,last_name,gender,date_of_birth,date_of_joining,status,company,department,designation,employment_type,branch,grade,default_shift
Employee A,EMP-0001,FirstA,LastA,Male,1990-01-15,2024-01-15,Active,Site A,Department A,Staff Nurse,Full-time,Site A,T2,Morning
Employee B,EMP-0002,FirstB,LastB,Female,1988-07-22,2023-06-01,Active,Site A,Department B,Senior Doctor,Full-time,Site A,T6,Morning
Employee C,EMP-0003,FirstC,LastC,Female,1995-03-10,2025-03-20,Active,Site A,Department C,Admin Executive,Full-time,Site B,T3,Evening
```

### Output (Frappe HR — `tabEmployee`)

| name | employee_name | employee_number | department | designation | default_shift | status | date_of_joining |
|------|---------------|-----------------|------------|-------------|----------------|--------|-----------------|
| `HR-EMP-00001` | Employee A | EMP-0001 | Department A | Staff Nurse | Morning | Active | 2024-01-15 |
| `HR-EMP-00002` | Employee B | EMP-0002 | Department B | Senior Doctor | Morning | Active | 2023-06-01 |
| `HR-EMP-00003` | Employee C | EMP-0003 | Department C | Admin Executive | Evening | Active | 2025-03-20 |

### Transformation notes

- **`name` (primary identifier) is auto-generated by Frappe HR.** The
  `HR-EMP-NNNNN` series shown above is **one** convention used by some
  deployments; the exact prefix and series rules are per-site configurable
  in `Naming Series` for the Employee DocType. The client CSV does NOT
  carry a `name` column. See Appendix A for the full naming-series table.
- **`employee_name` is the join key** between Employee and any record that
  Links back (Shift Request, Shift Assignment, Leave Application). The
  migration script builds a `employee_name → name` map once at run start
  (script: `dev_emp_by_name`) and rewrites every dependent Link using
  that map. **Implication for clients:** `employee_name` must be unique
  and spelled identically across all CSVs, **case-sensitive** on Linux
  MariaDB (Gotcha #6).
- **`status = Active`** is the Frappe HR default for new employees. Clients
  flip to `Left` via the Separation workflow, which is out of scope for the
  intake workbook.
- **`gender` and `default_shift`** are Link fields. Their target DocTypes
  (`Gender`, `Shift Type`) must exist on the target site BEFORE Employee
  inserts run (Gotcha #6). Migration order ensures this.
- **`company` field** in the client's spreadsheet is a Link to `tabCompany`.
  In single-tenant deploys the migration script pins it programmatically
  from session context (Gotcha #2); multi-tenant deploys preserve the CSV
  value verbatim.
- **Re-run semantics.** The upsert pattern is
  `frappe.db.exists(dt, name) → get_doc + update + save` else
  `new_doc + insert`. Re-running the migration after a partial failure
  resumes at the missing records; existing records are updated in place.
  No duplicates, no destructive rewrites.

## Example 2: Shift Assignment

### Input (raw Excel — `15_shift_assignment.csv`)

```csv
name,employee,employee_name,shift_type,company,start_date,end_date,status,shift_location
HR-SHA-2025-09-00001,HR-EMP-00001,Employee A,Morning,Site A,2025-09-01,2025-09-30,Active,Site A — Main Block
HR-SHA-2025-09-00002,HR-EMP-00002,Employee B,Evening,Site A,2025-09-01,2025-09-30,Active,Site A — Main Block
HR-SHA-2025-09-00003,HR-EMP-00001,Employee A,Night,Site A,2025-10-01,2025-09-30,Active,Site A — Main Block
```

### Output (Frappe HR — `tabShift Assignment`)

| name | employee | employee_name | shift_type | start_date | end_date | status | docstatus |
|------|----------|---------------|------------|------------|----------|--------|-----------|
| `HR-SHA-2025-09-00001` | `HR-EMP-00001` | Employee A | Morning | 2025-09-01 | 2025-09-30 | Active | 1 |
| `HR-SHA-2025-09-00002` | `HR-EMP-00002` | Employee B | Evening | 2025-09-01 | 2025-09-30 | Active | 1 |
| _rejected_ | _rejected_ | _rejected_ | _rejected_ | _rejected_ | _rejected_ | _rejected_ | _rejected_ |

### Transformation notes

- **Row 3 was REJECTED at save time** because `end_date < start_date`
  (`2025-09-30 < 2025-10-01`). The migration script's idempotent pattern
  (upsert + per-row `try/except`) means invalid rows are **logged and
  skipped, not fatal** — the script continues with the rest of the batch
  and reports `fail=1` in the per-DocType summary. Clients should
  pre-validate with Excel's `IF(D2<C2,"INVALID",…)` or with the
  settings checklist before submission.
- **`name` uses `autoname='prompt'`** (Gotcha #4). The CSV MUST carry a
  non-empty `name` column; without it Frappe raises
  `ValidationError: Naming Series 'prompt' is invalid` on insert. The
  migration script pins `name` explicitly on every row.
- **`employee` Link remap (Gotcha #7).** The CSV's `employee` column may
  carry the *source-system* Employee ID. The script replaces it with the
  *target-site* Employee `name` using `employee_name` as the join key
  (`dev_emp_by_name[employee_name] → name`). In this example the IDs
  happen to align, but in general they do not — the CSV MUST supply
  `employee_name` regardless.
- **`shift_schedule_assignment` is NULLIF'd (Gotcha #9).** Any value in
  this column on the source side is **discarded** by the script. Clients
  should leave the column blank in the CSV. (The linked
  `Shift Schedule Assignment` DocType is out of scope for this workbook.)
- **`shift_location` pre-create (Gotcha #9).** The script calls
  `_ensure_shift_location()` before processing any Shift Assignment,
  pre-creating a single canonical Shift Location so the Link resolves.
  If the client's CSV uses a non-canonical location name, populate
  `08_shift_location.csv` AND update the script's `_ensure_shift_location()`
  call to match — otherwise the canonical name silently wins.
- **`docstatus` is preserved from source.** `1` = Submitted (active);
  `0` = Draft (planning window); `2` = Cancelled. Cancelled records
  migrate alongside active ones.
- **`shift_request` Link** (optional) is preserved if the linked
  Shift Request exists on the target site. **Gotcha:** `Shift Request`
  migrates BEFORE `Shift Assignment` (migration order); missing SRs
  silently drop the Link without raising.

## Example 3: Attendance

### Input (raw Excel — `16_attendance.csv`)

```csv
employee,attendance_date,status,shift,leave_type,late_entry_by
Employee A,2025-09-15,Present,Morning,,0
Employee B,2025-09-15,Half Day,Morning,Sick Leave,15
Employee C,2025-09-15,On Leave,,Sick Leave,0
Employee D,2025-09-15,Absent,,,0
Employee A,2025-09-16,Present,Evening,,0
```

### Output (Frappe HR — `tabAttendance`)

| name | employee | attendance_date | status | shift | leave_type | late_entry_by |
|------|----------|-----------------|--------|-------|------------|---------------|
| `HR-ATT-2025-09-15-00001` | `HR-EMP-00001` | 2025-09-15 | Present | Morning | (empty) | 0 |
| `HR-ATT-2025-09-15-00002` | `HR-EMP-00002` | 2025-09-15 | Half Day | Morning | Sick Leave | 15 |
| `HR-ATT-2025-09-15-00003` | `HR-EMP-00003` | 2025-09-15 | On Leave | (empty) | Sick Leave | 0 |
| `HR-ATT-2025-09-15-00004` | `HR-EMP-00004` | 2025-09-15 | Absent | (empty) | (empty) | 0 |
| `HR-ATT-2025-09-16-00001` | `HR-EMP-00001` | 2025-09-16 | Present | Evening | (empty) | 0 |

### Transformation notes

- **`name` is per-day.** Frappe HR's naming series for Attendance
  (`HR-ATT-.YYYY-MM-DD.-#####`) resets each calendar day, so the
  counter restarts at `00001`. Clients don't supply this column.
- **One row per employee per day.** If a client submits two rows for the
  same employee on the same date (e.g., a morning Present row and an
  afternoon Half Day override), the second insert fails with
  `DuplicateEntryError`. Best practice: one consolidated row per
  employee per day; let half-day / late-entry be columns on that row.
- **`status` enum is enforced server-side.** Allowed values:
  `Present`, `Absent`, `On Leave`, `Half Day`, `Work From Home`,
  `Weekly Off`, `Holiday`, `Optional Holiday`. Any other value (e.g.,
  `"Late"` or `"WFH"`) raises `ValidationError` at save.
- **`shift` Link is optional.** When auto-attendance is enabled, the
  scheduler populates this from the employee's `Shift Assignment` for
  that date. The CSV lets HR override manually — useful when biometric
  data is missing or the employee swapped.
- **`leave_type` is required when `status` is `On Leave` or `Half Day`.**
  It Links to `tabLeave Type`. Missing it raises `LinkValidationError`.
- **`late_entry_by` is a custom field** (Rule #9 from the source site's
  intake). It is preserved by the upsert path but only if the target
  site has the matching custom field installed (verify via the
  custom-field fixture shipped with the deployment). If absent, the
  column is silently dropped.

## Example 4: Leave Application

### Input (raw Excel — `18_leave_application.csv`)

```csv
employee,leave_type,from_date,to_date,leave_half_day,half_day_date,reason,leave_approver
Employee A,Sick Leave,2025-09-20,2025-09-22,0,,Flu,user_a@example.com
Employee B,Earned Leave,2025-10-01,2025-10-03,0,,Family event,user_b@example.com
Employee C,Sick Leave,2025-09-25,2025-09-25,1,2025-09-25,Doctor appointment,user_c@example.com
```

### Output (Frappe HR — `tabLeave Application`)

| name | employee | leave_type | from_date | to_date | leave_half_day | status | leave_approver | total_leave_days |
|------|----------|------------|-----------|---------|----------------|--------|----------------|------------------|
| `HR-LAP-2025-09-00001` | `HR-EMP-00001` | Sick Leave | 2025-09-20 | 2025-09-22 | 0 | Approved | user_a@example.com | 3 |
| `HR-LAP-2025-10-00002` | `HR-EMP-00002` | Earned Leave | 2025-10-01 | 2025-10-03 | 0 | Open | user_b@example.com | 3 |
| `HR-LAP-2025-09-00003` | `HR-EMP-00003` | Sick Leave | 2025-09-25 | 2025-09-25 | 1 | Approved | user_c@example.com | 0.5 |

### Transformation notes

- **`name` is per-month.** Frappe HR's series for Leave Application
  (`HR-LAP-.YYYY.MM.-#####`) resets each calendar month.
- **`status` lifecycle.** Newly inserted records default to `Open` on
  insert. The Leave Approver then flips it to `Approved` or `Rejected`;
  either party can later set `Cancelled`. The migration script preserves
  whatever `status` the source CSV carries — but be aware that
  importing records already in `Approved` state bypasses the approver's
  workflow on the target site.
- **`total_leave_days` is calculated by Frappe HR** from
  `from_date` + `to_date` + `leave_half_day`, then minus any holidays
  in the employee's `Holiday List`, minus any overlap with already-
  approved leave. Clients should **NOT** pre-fill this column; leave it
  blank and let Frappe compute it.
- **`leave_approver` is a Link to `tabUser.email`** (NOT to
  `tabEmployee.name`). Common gotcha: clients paste an Employee's name
  or the employee's badge ID into this column, which raises
  `LinkValidationError`. Use the approver's login email.
- **`half_day_date` is required when `leave_half_day = 1`.** When the
  CSV has `half_day=1` with a blank `half_day_date`, Frappe defaults to
  `from_date`. Verify the result after migration.
- **Same gotcha-7 ID-remap applies.** The migration script rewrites
  `employee` from the source ID to the target-site ID using
  `employee_name` as the join key (matching the pattern shown in
  Example 2). The client's CSV may carry either ID; the script handles
  both.

## Appendix A — Naming series reference

> The exact prefix and series pattern for each DocType is configurable
> per site via **Naming Series** in the DocType's settings. The table
> below shows **one** convention used in production deployments —
> verify with the client before signing off on the report.

| DocType              | Naming series pattern          | Series key                                | Example                  |
|----------------------|--------------------------------|-------------------------------------------|--------------------------|
| Employee             | `HR-EMP-.YYYY.-#####`          | per calendar year                          | `HR-EMP-2025-00001`     |
| Department           | `field:department_name`        | value of `department_name`                | `Department A`           |
| Designation          | `field:designation_name`       | value of `designation_name`               | `Staff Nurse`            |
| Employment Type      | `field:name`                   | value of `name`                           | `Full-time`              |
| Employee Grade       | `field:grade_name`             | value of `grade_name`                     | `T2`                     |
| Branch               | `field:branch`                 | value of `branch`                         | `Site A`                 |
| Holiday List         | `field:holiday_list_name`      | value of `holiday_list_name`              | `State A Holiday Calendar 2026`         |
| Shift Type           | `prompt` (manual)              | client-supplied in `name` column          | `Morning`                |
| Shift Location       | `field:location_name`          | value of `location_name`                  | `Site A — Main Block`    |
| Shift Schedule       | `prompt` (manual)              | client-supplied in `name` column          | `Sched-A`                |
| Shift Request        | `HR-SHR-.YY.MM.-#####`         | per calendar month; autoname Series        | `HR-SHR-25-09-00001`    |
| Shift Assignment     | `HR-SHA-.YYYY.MM.-#####`       | per calendar month (script pre-bumps)     | `HR-SHA-2025-09-00001`   |
| Attendance           | `HR-ATT-.YYYY-MM-DD.-#####`    | per calendar day                          | `HR-ATT-2025-09-15-00001` |
| Leave Application    | `HR-LAP-.YYYY.MM.-#####`       | per calendar month                        | `HR-LAP-2025-09-00001`   |
| Leave Allocation     | `HR-LAL-.YYYY.MM.-#####`       | per calendar month                        | `HR-LAL-2025-09-00001`   |
| Leave Ledger Entry   | `HR-LLE-.YYYY.MM.DD.-#####`    | per calendar day                          | `HR-LLE-2025-09-15-00001` |

> **Why this matters for reconciliation.** When the client looks at
> records in the Frappe HR list view, the `name` column is what they
> see — not the CSV's `employee_name` or `employee_number`. The
> mapping doc and the appendix here exist so the client can verify
> "this `HR-EMP-NNNNN` corresponds to Employee A in our spreadsheet".

## Appendix B — Reconciliation report format (for client sign-off)

After migration, generate a per-DocType reconciliation report and
share with the client's HR Manager for sign-off.

```csv
doctype,raw_rows_received,rows_imported,rows_skipped,skip_reasons
Employee,210,210,0,
Shift Type,25,25,0,
Shift Assignment,8000,7820,180,"invalid date ranges; duplicate names"
Attendance,4500,4500,0,
Leave Application,180,180,0,
```

### How to read the report

- **`raw_rows_received`** — count of data rows in the client's CSV
  (excluding the header).
- **`rows_imported`** — `inserted + updated` from the migration
  script's per-DocType summary line
  (`RESULT <DocType>: ins=N upd=M fail=K`).
- **`rows_skipped`** — `raw_rows_received − rows_imported − fail`.
  Skipped rows cover: root-node filters (Department), validation
  failures caught by the script, and CSV-level rejections
  (bad encoding, missing headers).
- **`skip_reasons`** — short prose summary, comma-separated. Examples:
  `"invalid date ranges"`, `"duplicate names"`, `"missing required
  fields (gender, default_shift)"`.

### Sign-off checklist

- [ ] `rows_imported == raw_rows_received` for every DocType, OR the
      `skip_reasons` column explains every shortfall.
- [ ] Spot-check 5 random `name` values per DocType against the
      source CSV — verify the `name` corresponds to the expected
      `employee_name`.
- [ ] Spot-check the `employee` Link on 5 random Shift Assignment
      rows — verify it points to the correct Employee `name` (not
      the source-system ID). This validates Gotcha #7.
- [ ] Confirm no `name` collisions (two CSV rows mapping to the
      same Frappe HR `name`) exist in any DocType.
- [ ] HR Manager signs the per-DocType sign-off template
      (`03_signoff/01_per_doctype_signoff_template.md`).
