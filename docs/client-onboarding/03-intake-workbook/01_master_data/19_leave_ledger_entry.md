# Leave Ledger Entry — Intake Sheet

**DocType:** `Leave Ledger Entry` (submittable)
**Module:** HR / Leave Management
**Required fields:** 7
**Optional fields:** 6+

> **Note:** Leave Ledger Entry is the **append-only audit trail** of all leave balance movements. It is normally auto-generated by Leave Allocation (Allocation), Leave Application (Application), and Encashment workflows. This sheet is for **manual corrections only** — backdated allocations, retroactive encashments, or balance restorations after a manual ledger fix.

## Healthcare-specific fields

None required — Leave Type and Employee provide hospital context.

## Validation rules

- `transaction_type=Expiration` requires `leaves_expired > 0`.
- `transaction_type=Encashment` requires `amount` populated.
- `transaction_type=Allocation` typically sets `leaves_added > 0`; `Application` typically sets `leaves_added < 0`.
- `leaves` (the post-transaction balance) is computed as the previous balance + `leaves_added`. If supplied manually, it must match the computed value — Frappe validates.
- `docstatus=2` (Cancelled) reverses the transaction; the balance recomputes from the remaining ledger entries.

## Common client mistakes

- Supplying `leaves` (post-balance) that contradicts `leaves_added` (delta) — Frappe rejects on save.
- Using `transaction_type=Application` without `leave_application` link — breaks traceability to the originating request.
- Using `transaction_type=Allocation` without `leave_allocation` link — breaks traceability.
- Setting `leaves_expired` on non-Expiration transactions — silently dropped by Frappe.
- Cancelling (`docstatus=2`) the wrong ledger entry — affects ALL downstream balance calculations for that employee + leave type.
- Forgetting `transaction_type` — defaults to `Manual`, which is fine for ad-hoc corrections but miscategorises the entry in audit reports.

## When to use this sheet

| Scenario | Use this sheet? |
|---|---|
| Standard leave application approval | **No** — Leave Application auto-creates Application row |
| Standard leave allocation | **No** — Leave Allocation auto-creates Allocation row |
| Retroactive encashment correction | **Yes** — manual Encashment row |
| Balance restoration after data fix | **Yes** — manual Allocation row with note |
| Carry-forward from previous period | **No** — Leave Allocation handles via `carry_forward=1` |
| Backdated leave application (legacy system) | **Yes** — manual Application row |

## Migration notes (post-go-live upload)

- **Employee ID remap by `employee_name`.** Same constraint as the other three transaction templates (GOTCHA #7). The upload script remaps `employee` using `employee_name` as the join key. Client CSV MUST supply both columns.
- **Ledger is append-only.** Frappe enforces this via the `LeaveLedgerEntry.on_cancel()` hook — cancelling a Submitted entry does NOT delete it; it inserts a compensating `Manual` row with the inverse delta. Never re-import a Cancelled entry with the same `name` — use a new `Manual` entry instead.
- **`leaves` (balance) is validated against the running balance.** The Frappe controller checks that `leaves = prev_balance + leaves_added` and rejects mismatches. The upload script pre-computes the expected running balance per (employee, leave_type) before insert; rows that would invalidate the sequence are skipped with a warning.
- **`leave_application` and `leave_allocation` must exist.** Optional Links are validated against the target site — if the referenced Leave Application / Leave Allocation row does not exist, the Link is dropped (Frappe does not raise on missing optional Links at insert time).
- **`docstatus=1` (Submitted) is required.** Draft ledger entries do NOT contribute to the Leave Balance calculation shown on Employee dashboards. Submit all imported rows to make the balance visible.
- **Transaction ordering matters.** Ledger entries are processed in `transaction_date` order (then `creation` order for ties). Out-of-order imports are allowed but recompute balances per-entry, so the FINAL balance reflects the last-inserted row per (employee, leave_type). Upload in chronological order to avoid confusion in audit reports.
