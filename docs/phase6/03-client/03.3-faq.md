## General

### What is ERPNext?

**ERPNext** is open-source Enterprise Resource Planning software — a single system that handles accounting, inventory, sales, buying, HR, payroll, manufacturing, projects, and CRM. It's built on the **Frappe** web framework and is one of the most widely deployed ERPs in the world, especially in India where it has strong GST, TDS, PF, and ESI support out of the box.

For Haritha Hospitals, ERPNext is the foundation — we use its HR module (HRMS) as the core, with our custom app `haritha_hospital` layered on top for hospital-specific tweaks.

### What is HRMS?

**HRMS** is the Human Resource Management System app for Frappe. It covers everything HR + payroll:

- Employee master record
- Attendance (auto + manual)
- Shift Management (Shift Types, Shift Assignments, Roster)
- Leave (Types, Allocations, Applications, Block Lists)
- Holidays
- Payroll (Salary Structures, Salary Slips, Payroll Entries)
- Recruitment, Training, Appraisal, Performance
- Loans, Expense Claims, Tax Declarations

Haritha uses HRMS as its primary app — Phase 1–4 of the project focused on Shift + Attendance + Leave + Employee master. Other HRMS modules are available as Haritha's HR team grows.

### Why did Haritha Hospitals choose ERPNext?

Five reasons:

1. **Open source** — no per-user licensing fees; total cost of ownership is much lower than SAP or Oracle
2. **HRMS-first design** — the HR module is first-class, not an afterthought
3. **India-aware** — built-in support for GST, TDS, PF, ESI, Professional Tax, e-invoicing
4. **Self-hostable** — full control of data, no vendor lock-in
5. **Customizable without forking** — Custom Fields + Custom App pattern lets us add 274 hospital-specific tweaks without touching core code

### Is Haritha Hospitals ERPNext cloud or on-premise?

**Both, your choice.**

- **Default deployment:** self-hosted on a VPS (we use DigitalOcean / Linode / equivalent). You own the server, the data, and the code.
- **Cloud option:** we can deploy on AWS / GCP / Azure / DigitalOcean managed Kubernetes if you prefer not to manage the VPS.
- **Hybrid:** self-hosted primary + managed backup destination on a separate region.

Either way, you own the database. We don't hold your data hostage.

### What's the data ownership model?

You own 100% of the data. Specifically:

- **Database** — your MariaDB, your server, your backup
- **Code customizations** — your GitHub repo, your fork
- **Files / attachments** — your filesystem, your S3 (if configured)
- **User accounts** — your User DocType, your authentication
- **Audit trail** — every change has author + timestamp + before/after; stored in your DB

If you stop working with us, your hospital keeps running. The system doesn't phone home. There's no "call us to unlock your data" — you have root.

## Technical

### How is data backed up?

**3-2-1 rule:**

- **3** copies of every backup
- **2** different media (local disk + remote disk)
- **1** offsite (geographically separate location)

**Schedule:** automated daily backup via cron. Backup file = full MariaDB dump + sites directory tarball. SHA256 checksum computed and verified.

**Offsite:** daily push to a separate VPS via rsync. The offsite VPS is in a different region / different provider to survive a single-provider outage.

**Verification:** automated SHA256 verification at offsite destination; daily heartbeat checks confirm last backup present and matching.

**Retention:** 30 days of daily backups kept on local, 90 days on offsite.

### How is security handled?

**Role-Based Access Control (RBAC):**
- Every user has one or more Roles
- Every Role has read/write/create/submit permissions per DocType
- Field-level permissions (e.g., a user can see but not edit Salary Slip amounts)
- Document-level permissions (e.g., HR Manager sees all employees; Team Lead sees only their team)

**Audit trail:**
- Every change to every record is logged with author + timestamp + before/after
- Viewable in the DocType's "Timeline" sidebar
- Searchable via Reports

**Encryption:**
- TLS in transit (Let's Encrypt cert, auto-renewed)
- Passwords hashed (bcrypt) — never stored in plaintext
- Database at rest (unencrypted by default; can be encrypted at filesystem level if your VPS supports it)

**Network:**
- VPN / Tailscale recommended for admin access
- IP allowlist available
- 2FA available for User accounts

**Compliance:**
- Audit-ready: every financial transaction has a creator, approver, and GL impact
- Statutory reports generated on demand (TDS, PF, ESI)

### What happens if our server crashes?

**Disaster Recovery (DR) runbook is documented and tested.**

Recovery procedure:

1. **Detect** — heartbeat monitor alerts within 15 minutes of downtime
2. **Provision** — spin up new VPS (any provider; we use the same image)
3. **Restore DB** — pull latest offsite backup, verify SHA256, restore to new MariaDB
4. **Restore sites** — pull latest offsite sites tarball, untar to `/home/frappe/frappe-bench/sites/`
5. **Update DNS** — point DuckDNS to new VPS IP
6. **Verify** — login, check critical records, validate Roster renders
7. **Communicate** — notify users when back online

**Targets:**

| Metric | Target | Notes |
|---|---|---|
| **RTO** (Recovery Time Objective) | 2 hours | From crash detection to full operation |
| **RPO** (Recovery Point Objective) | 24 hours | Maximum data loss = one day's transactions |

We've tested this. The most recent successful recovery drill is documented in the runbook.

### Can we self-host?

**Yes.** The entire stack is Docker Compose-based and runs on any Linux VPS with:

- 4 GB RAM minimum (8 GB recommended for 200+ employees)
- 50 GB disk minimum (100 GB recommended for 1-year retention)
- Docker + Docker Compose installed
- Public IP (or NAT with port forwarding)
- DuckDNS or your own domain

We provide the `compose.yaml`, env file templates, and step-by-step setup guide. Most clients are up in a day.

### How are updates handled?

**Two paths:**

1. **Frappe / ERPNext / HRMS upstream updates** — quarterly. We test the upgrade on dev → staging → prod. Typical effort: 1–2 days per upgrade, including regression test of customizations.
2. **Custom app updates** — `haritha_hospital` itself. New features / bug fixes / new hospital-specific customizations. Deployed as new commits to your GitHub repo; you `git pull` and `bench migrate`.

**Schema changes** (e.g., new Custom Fields) are versioned in the custom app and applied via `bench migrate`. Existing data is preserved.

**Breaking changes** are documented in CHANGELOG.md with a migration guide.

## Customization

### Can we add custom fields?

**Yes, in three ways:**

1. **Via UI** — Settings → Customize → Add Custom Field. Works for quick additions. **Caveat:** not version-controlled; only lives in your DB.
2. **As fixtures in our custom app** — declare in `apps/haritha_hospital/haritha_hospital/fixtures/custom_field.json`, deploy via `bench migrate`. Version-controlled, env-portable, idempotent. **Recommended.**
3. **As a new DocType** — for entirely new entities (not just fields on existing ones). Documented in `apps/haritha_hospital/haritha_hospital/doctype/`.

### Can we integrate with our biometric device?

**Yes.** HRMS Employee Checkin is the universal input point for any biometric / RFID / GPS system.

Three integration patterns:

1. **Direct API** — POST to `/api/resource/Employee Checkin` with `{employee, time, log_type, device_id}` from your device's middleware. Most common pattern.
2. **Webhook from device vendor** — most vendors (ZKTeco, eSSL, Realtime, Mantra) have webhook support; point them at our endpoint.
3. **File upload** — many vendors export CSV / Excel of daily punches. HRMS has a bulk-upload tool.

We provide an integration guide for the major biometric vendors used in Indian hospitals.

### Can we add custom reports?

**Yes.** Two kinds:

1. **Query Report** — write SQL, save as DocType, expose in Reports menu. Best for tabular reports.
2. **Script Report** — write Python (with access to Frappe ORM), save as DocType, expose in Reports menu. Best for reports needing business logic or joining multiple DocTypes.

We can build any report your team needs. Typical turnaround: 2-5 days per report.

### Can we customize the payroll formulas?

**Yes.** Every Salary Component has a formula field (Python expression). Add / modify components, change formulas, your payroll adapts.

Example: `Basic * 0.4 + 5000` for an HRA component.
