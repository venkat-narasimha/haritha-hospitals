## Slide 3 — The Challenge

**Hospital operations don't run 9-to-5. Most HR systems do.**

- **24/7 operations** — ICU night, emergency, security all need rostered coverage
- **200+ employees across 36 departments** (Nursing, Pharmacy, Lab, Housekeeping, Security, Admin, Billing, …)
- **Shift scheduling errors = patient safety risk** (not just an HR problem)
- **Manual attendance reconciliation** — phone calls, paper registers, biometric logs that don't match HR
- **Payroll disputes** from shift mismatches and missed punch corrections
- **No single source of truth** — same employee lives in 3 systems (biometric, Excel, payroll tool)

[Visual: 6 pain-point icons in a 2×3 grid. Use hospital-appropriate imagery: nurse, clock, biometric, payroll, Excel icon, question mark.]

## Slide 7 — Shift Management — Our Differentiator ⭐

**The single most-used screen at Haritha. The HR manager opens this first thing every morning.**

- **25 predefined shift types** with a strict 10-character naming convention:
  - `G0900R0830` → General, 09:00 start, Regular, 8h 30m
  - `M0600R0830` → Morning, 06:00 start (ICU ward)
  - `A1200R0830` → Afternoon, 12:00 start
  - `N2000R1200` → Night, 20:00 start, 12h (ICU night, crosses midnight)
- **Color-coded Roster SPA** (Vue 3 + Tailwind) — G/M/A/N map to blue/green/orange/violet
- **Monthly grid** at `/hr/roster` — every employee × every day, instant visual coverage
- **Drag-and-drop reassignment** for sudden absences
- **Geo-fenced check-in** — 200m radius around the Hyderabad hospital location
- **Auto-attendance** — scheduler reads `Employee Checkin` every minute, pairs IN/OUT, marks Present / Absent / On Leave / Half Day / Holiday
- **Grace periods** — 60 min early-in, 60 min late-out, 5-hour half-day threshold
- **Shift swap requests** — multi-level approval via custom field `shift_request_approver`
- **Holiday-aware** — scheduled shift on a holiday auto-marks as "Holiday" (paid)


## Appendix A — Glossary

| Term | Meaning |
|---|---|
| **ERPNext** | Open-source ERP — accounting, inventory, sales, buying, HR, payroll, manufacturing |
| **Frappe** | The Python + Vue web framework ERPNext and HRMS are built on |
| **HRMS** | The HR + payroll app for Frappe; ships with ERPNext |
| **DocType** | A Frappe schema entity — like a database table + form + REST endpoint combined |
| **Custom Field** | A field added to an existing DocType (e.g., `Employee.default_shift`) |
| **Property Setter** | A property overridden on an existing DocField (e.g., dropdown options) |
| **Fixture** | A JSON export of metadata (Custom Fields, Property Setters, Print Formats) version-controlled in the custom app |
| **Shift Type** | Template for a shift (timing, color, grace periods) |
| **Shift Assignment** | One row = "Employee X works Shift Type Y from date A to date B" |
| **Employee Checkin** | Raw IN/OUT log entry (biometric / mobile / manual) |
| **Attendance** | Derived per-day status — Present / Absent / On Leave / Half Day / Holiday |
| **Salary Slip** | One per employee per month — earnings + deductions + net pay |
| **SPA** | Single-page application (the HRMS Roster is a Vue 3 SPA) |
| **RTO / RPO** | Recovery Time / Recovery Point Objective (DR metrics) |
| **3-2-1 backup** | 3 copies, 2 media, 1 offsite |

## Appendix C — Security Architecture

**Defense in depth.**

| Layer | Mechanism |
|---|---|
| **Transport** | TLS (Let's Encrypt, auto-renewed). HSTS-ready. |
| **Authentication** | Password (bcrypt-hashed) + 2FA available. Session timeout configurable. |
| **Authorization** | Role-Based Access Control (RBAC) per DocType — read / write / create / submit / cancel. Field-level and document-level permissions supported. |
| **Audit trail** | Every change: author + timestamp + before/after JSON. Viewable in DocType "Timeline" sidebar. Searchable via Reports. |
| **Network** | VPN / Tailscale recommended for admin access. IP allowlist available. |
| **Data at rest** | MariaDB on encrypted filesystem (LUKS) optional. |
| **Backups** | Encrypted in transit (rsync over SSH), SHA256-verified at destination. |
| **Compliance** | Audit-ready: every financial transaction has creator, approver, GL impact. Statutory reports on demand (TDS, PF, ESI). |
| **Incident response** | Documented runbook (04.4) — severity classification, triage flow, escalation matrix. Tested in production (2026-08-29 500-outage case study). |
| **Disaster recovery** | Documented runbook (04.3). RTO 2 hours, RPO 24 hours, tested. |
| **Code customizations** | Version-controlled in your GitHub repo. No "vendor hold" on patches. |
| **Data ownership** | You own 100% — DB, code, files, user accounts, audit trail. |
