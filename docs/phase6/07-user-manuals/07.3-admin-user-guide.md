## System overview

The Haritha Hospitals ERPNext system runs on a single VPS (main + offsite) with three environments:

| Env | URL | Purpose |
|---|---|---|
| **pberpdev** | `https://pberpDEV.duckdns.org/` | Development — schema experiments, fixture testing |
| **pberpqa** | `https://pberpqa.duckdns.org/` | Pre-prod gate — currently skipped for Haritha work |
| **pberpprod** | `https://pberpprod.duckdns.org/` | Production — live users |

Each env is a Docker Compose stack:

- Backend (gunicorn, Frappe workers)
- DB (MariaDB)
- Scheduler (cron jobs, scheduled tasks)
- Queue (background jobs)

Customizations live in the `haritha_hospital` app (workspace: `projects/haritha-hospitals/`, repo: `git@github.com:venkat-narasimha/haritha_hospital.git`). As of 2026-08-29, the app captures 274 customizations: 78 Custom Fields + 189 Property Setters + 3 Print Formats + 2 Notifications + 2 Letter Heads.

> Architecture recap: see [00.2 Architecture Overview](../00-foundations/00.2-architecture-overview.md).

## App management

### haritha_hospital app — what it does

The custom app captures all Haritha-specific customizations as code:

- 78 Custom Fields (e.g. `Shift Type.is_oncall`, `Employee.blood_group`)
- 189 Property Setters (e.g. `Shift Type.color = #hex` for roster SPA colors)
- 3 Print Formats (Salary Slip, Leave Application, Offer Letter)
- 2 Notifications (leave approval, shift swap)
- 2 Letter Heads (Haritha Hospitals branded PDFs)

The app is **env-portable**: install on a fresh env → all 274 customizations apply automatically. No more "prod has a field dev doesn't" drift.

### Update flow (dev → prod)

1. **Dev** (local workspace):
   - Edit `haritha_hospital/fixtures/*.json` or `haritha_hospital/hooks.py`
   - Test on pberpdev: `bench --site pberpDEV.duckdns.org console` + UI verify
   - Commit: `git add . && git commit -m "<msg>"` (identity: venkat-narasimha / srivenkatnarasimha@gmail.com)
2. **Promote to QA** (pberpqa):
   - `ssh vijay@144.217.163.228 "cd /home/vijay/frappeclaw/frappeclaw-data/workspace/projects/haritha_hospital && git pull"`
   - `bench --site pberpqa.duckdns.org migrate`
   - Smoke test
3. **Promote to Prod**:
   - Same `git pull` + `bench --site pberpprod.duckdns.org migrate`
   - **Always** `docker restart erp-prod-backend-1` after install-app or major code change (LEARNINGS #153)

### Fixtures re-tag workflow (when adding new customizations)

If you create a new Custom Field in pberpprod UI:

1. **Don't leave it there** — it becomes prod-only drift.
2. Re-tag it to the haritha_hospital module:
   - `Custom Field` → edit → set `Module = haritha_hospital` → save
3. Re-export fixtures:
   ```bash
   bench --site pberpprod.duckdns.org export-fixtures --app haritha_hospital
   ```
4. Verify `haritha_hospital/fixtures/custom_field.json` includes the new field.
5. Commit + push.

> **Hooks requirement (LEARNINGS #151):** `fixtures = [...]` must be declared in `haritha_hospital/hooks.py`. Without it, `export-fixtures` exits 0 with no files written (silent no-op). Current declaration:
>
> ```python
> fixtures = [
>     {"doctype": "Custom Field", "filters": {"module": "haritha_hospital"}},
>     {"doctype": "Property Setter", "filters": {"module": "haritha_hospital"}},
>     {"doctype": "Print Format", "filters": {"module": "haritha_hospital"}},
>     {"doctype": "Notification", "filters": {"module": "haritha_hospital"}},
>     {"doctype": "Letter Head", "filters": {"module": "haritha_hospital"}},
> ]
> ```

## Customization

### Adding a Custom Field (UI + code)

**UI method** (quick, for one-off):

1. Settings → Customize → Custom Field → New.
2. Pick DocType (e.g. Employee).
3. Add field: label, fieldname, fieldtype, options.
4. **Module = haritha_hospital** (critical for fixture capture).
5. Save.
6. Re-export fixtures (see above).

**Code method** (for version control):

1. Edit `haritha_hospital/fixtures/custom_field.json`.
2. Add entry with all required fields:
   ```json
   {
     "doctype": "Custom Field",
     "dt": "Employee",
     "fieldname": "blood_group",
     "label": "Blood Group",
     "fieldtype": "Select",
     "options": "A+\nA-\nB+\nB-\nAB+\nAB-\nO+\nO-",
     "module": "haritha_hospital",
     "insert_after": "emergency_contact"
   }
   ```
2. Commit + push.
3. `bench --site pberpprod.duckdns.org migrate` (loads fixtures).

### Adding a Property Setter

Property Setters modify stock fields (change field type, hide, set color, etc.). Example — set Shift Type color:

1. Settings → Customize → Property Setter → New.
2. DocType = Shift Type, Property = `color`, Value = `#FF8C00` (orange for Afternoon).
3. Module = haritha_hospital.
4. Save + re-export fixtures.

Common uses:

- **`color`** on Shift Type (drives roster SPA)
- **`hidden`** to hide a stock field
- **`options`** to narrow a Select
- **`read_only`** to lock a field from non-admin edits
- **`default`** to prefill values

### Adding a Print Format

1. Settings → Printing → Print Format → New.
2. Pick DocType (e.g. Salary Slip).
3. Write Jinja-templated HTML (or use the UI builder).
4. Module = haritha_hospital.
5. Add to fixtures (`print_format.json`).

> **Test:** Preview with sample data → PDF → verify letter head + layout → commit.

### Exporting as fixtures

```bash
bench --site <site> export-fixtures --app haritha_hospital
```

Files written to `haritha_hospital/fixtures/`:

- `custom_field.json`
- `property_setter.json`
- `print_format.json`
- `notification.json`
- `letter_head.json`
- (any other DocTypes in `hooks.py:fixtures`)

### Verifying fixtures

```bash
# Count customizations per file
jq 'length' haritha_hospital/fixtures/custom_field.json   # expect 78
jq 'length' haritha_hospital/fixtures/property_setter.json # expect 189
jq 'length' haritha_hospital/fixtures/print_format.json   # expect 3
jq 'length' haritha_hospital/fixtures/notification.json   # expect 2
jq 'length' haritha_hospital/fixtures/letter_head.json    # expect 2

# Sanity: all CF/PS rows tagged correctly
jq '[.[] | select(.module != "haritha_hospital")]' haritha_hospital/fixtures/custom_field.json
# Should be empty []
```

## User & permission management

### Creating users

1. Settings → User → New.
2. Email (must be unique).
3. First Name, Last Name.
4. **Roles** child table — add appropriate roles (Employee, HR Manager, HR User, etc.).
5. **Module Profile** — optional, bundles roles.
6. Save.
7. System sends invite email with temp password.

> **Test users** (e.g. for QA): use `+test1@harithahospitals.in` aliases; do not pollute real user list.

### Role assignment

Built-in roles (used at Haritha):

- **Administrator** — full access
- **System Manager** — settings, users, permissions (no transactions)
- **HR Manager** — full HR module
- **HR User** — read-only HR + own records
- **Employee** — self-service only
- **Employee Self Service** — subset of Employee (limited views)
- **Accounts Manager**, **Accounts User** — finance (not used currently)
- **Leave Approver** — can approve leaves only

### Custom roles

For fine-grained access:

1. Settings → Role → New.
2. Name (e.g. `Nurse Roster Editor`).
3. Description.
4. Permissions: child table (DocType + level).
5. Save.

> **Custom roles rarely needed.** Reuse built-in roles where possible.

### Permission rules (DocType-level, field-level)

**DocType-level** (Settings → Role Permissions):

- For each role × DocType combo: read / write / create / delete / submit / cancel / amend flags.

**Field-level** (rare):

- Property Setter with `property = permlevel` or custom perm rules.

**Row-level** (User Permissions):

- Settings → User Permission → assign what records a user can see.
- Example: HR manager can only see Employees in `Department = Cardiology`.

> **Verify:** After any role/permission change, log in as that user (or impersonate via `bench --site X console frappe.session.user = 'X'`) and check access.

## Master data

### Departments, Designations, Shift Types, Locations

**Naming conventions** (critical for consistency — see `masters/shift_type.csv`):

- **Department:** Title Case, full name (`Cardiology`, `Pediatrics`, `Emergency Medicine`)
- **Designation:** Title Case (`Staff Nurse`, `Senior Consultant`, `Resident Doctor`)
- **Shift Type:** `[Period][HHMM][R/S][HHMM]`
  - Period: `G` (General), `M` (Morning), `A` (Afternoon), `N` (Night)
  - HHMM = 24-hour start time
  - `R` = Regular (single block), `S` = Splits past midnight
  - Last HHMM = end time
  - Example: `M0800R0830` = Morning 08:00, Regular, ends 08:30 next day = 24.5h ... actually 08:00 → 16:30 = 8.5h
- **Location:** Building / Floor / Wing (`Main Block`, `ICU 1st Floor`, `OP Wing`)

### Holiday Lists

1. Human Resources → Holiday List → New.
2. Add holidays row-by-row (date, name).
3. Set weekly offs (typically Sundays).
4. Assign to Department or Employee via Employee record → Holiday List field.

> **Single source of truth:** "Haritha Hospitals Holiday List" — all departments share. No per-department lists unless absolutely needed.

## Performance monitoring

### Container health

```bash
# All 4 envs, all containers
ssh vijay@144.217.163.228 \
  "docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}' \
   | grep -E 'erp-(prod|qa|dev)-(backend|db|scheduler|queue)-1'"

# Look for: RestartCount > 0, Up X minutes (not hours), Exited state
docker inspect <container> --format '{{.State.RestartCount}} {{.State.StartedAt}}'
```

> See [04.2 Daily Ops Runbook](../04-runbooks/04.2-daily-ops.md) for daily cadence.

### DB queries (slow query log)

```bash
# Enable slow query log
docker exec erp-prod-db-1 bash -c \
  "mysql -uroot -p\"$MYSQL_ROOT_PASSWORD\" -e \
   \"SET GLOBAL slow_query_log = 'ON'; \
    SET GLOBAL long_query_time = 2;\""

# Tail slow log
docker exec erp-prod-db-1 tail -f /var/log/mysql/slow.log

# Disable after session
docker exec erp-prod-db-1 mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
  -e "SET GLOBAL slow_query_log = 'OFF';"
```

> **Default threshold:** 2 seconds. Adjust per need.

### Worker count tuning

Edit `frappe_docker/compose.yml` or `common_site_config.json`:

```json
{
  "workers": {
    "background_workers": 4,
    "short_workers": 4,
    "long_workers": 4
  }
}
```

After change: `docker compose up -d` (full restart of worker containers).

> **Rule of thumb:** 1 worker per ~25 concurrent users. Haritha has ~250 employees, ~80 concurrent users → 4 workers each is enough.

## Troubleshooting

### Common errors + fixes

| Error | Likely cause | Fix |
|---|---|---|
| `500 Server Error` after `install-app` | gunicorn `--preload` sys.path not refreshed | `docker restart erp-prod-backend-1` (LEARNINGS #153) |
| `ImportError: No module named haritha_hospital` | app not in `apps.txt` or no backend restart | Check `apps.txt`, restart backend |
| `Permission denied` for routine action | User missing role | Settings → User → add role |
| Login fails with `401` | DB password mismatch | Re-verify via `printenv` (LEARNINGS #154, #157) |
| `Connection refused` to DB | DB container down | `docker ps`; restart if down |
| `bench backup` exit 1 | hrms ghost in `installed_apps` (Lesson #57) | Edit `tabInstalled Application` row |
| Roster SPA blank | Custom Field not loaded | `bench migrate`; verify `haritha_hospital` installed |
| Print Format missing | Letter Head deleted | Restore from fixtures; re-tag module |

See [04.4 Incident Response Plan](../04-runbooks/04.4-incident-response.md) for full triage flow.

## Upgrades

### Frappe / ERPNext / HRMS upgrade procedure

1. **Backup first** (always):
   ```bash
   bench --site <site> backup --with-files
   ```
2. **Pull new image**:
   ```bash
   cd /home/vijay/frappeclaw
   docker compose pull
   ```
3. **Run migrations**:
   ```bash
   bench --site <site> migrate
   ```
4. **Restart all**:
   ```bash
   docker compose restart
   ```
5. **8-phase test** (per [08.3 Regression Test Script](../08-testing/08.3-regression-script.md))
6. **Smoke test in browser**: login, load key DocTypes.

### haritha_hospital compatibility check

Before any upgrade:

```bash
cd /home/vijay/frappeclaw/frappeclaw-data/workspace/projects/haritha_hospital
git log --oneline -10  # recent commits
git status  # clean?
```

Check if any fixtures reference deprecated fields. Grep `fixtures/*.json` for the fieldname before migrating.

### Pre-upgrade checklist

- [ ] Backup taken + SHA256 verified
- [ ] haritha_hospital on clean commit, no uncommitted changes
- [ ] No active long-running jobs (pause scheduler)
- [ ] No users logged in during upgrade window
- [ ] Maintenance window communicated (24h notice)
- [ ] Rollback plan documented (last working image tag)

## Security

### DB password rotation

**When:** quarterly or after any suspected leak.

```bash
# 1. Backup
bench --site pberpprod.duckdns.org backup --with-files

# 2. Edit docker-compose.yml → MYSQL_ROOT_PASSWORD=newpassword
ssh vijay@144.217.163.228 "vim /home/vijay/frappeclaw/docker-compose.yml"

# 3. Restart db container
ssh vijay@144.217.163.228 \
  "cd /home/vijay/frappeclaw && docker compose up -d db"

# 4. Update site_config.json
ssh vijay@144.217.163.228 \
  "docker exec erp-prod-backend-1 bash -c \
   \"python -c \\\"import json; \
     c = json.load(open('/home/frappe/frappe-bench/sites/pberpprod.duckdns.org/site_config.json')); \
     c['db_password'] = 'newpassword'; \
     json.dump(c, open('/home/frappe/frappe-bench/sites/pberpprod.duckdns.org/site_config.json', 'w'))\\\"\""

# 5. Restart backend
ssh vijay@144.217.163.228 "docker restart erp-prod-backend-1"

# 6. Verify login
bench --site pberpprod.duckdns.org console
# → if console opens, password works

# 7. Update MEMORY.md
```

- **One key per host** (no reuse).
- Store in `/root/.openclaw/{ssh_key,venkat_vps_key,pberpqa_backup_key,...}`.
- `chmod 600` on private key.
- Rotate annually.
- Revoke on personnel change.

## Audit log review

Periodic checks (monthly recommended):

```bash
# Recent schema changes
bench --site pberpprod.duckdns.org console
>>> frappe.db.sql("SELECT creation, modified, modified_by FROM `tabCustom Field` WHERE creation > NOW() - INTERVAL 30 DAY")
>>> frappe.db.sql("SELECT creation, modified, modified_by FROM `tabProperty Setter` WHERE creation > NOW() - INTERVAL 30 DAY")

# User login anomalies
>>> frappe.db.sql("SELECT user, MAX(time) FROM `tabActivity Log` WHERE creation > NOW() - INTERVAL 7 DAY GROUP BY user")

# Failed logins
>>> frappe.db.sql("SELECT * FROM `tabActivity Log` WHERE status='Failed' AND creation > NOW() - INTERVAL 7 DAY")
```

> **Anomaly response:** Multiple failed logins from one IP → possible brute force → block IP. New custom fields outside haritha_hospital module → drift → re-tag.
